# Pinkbox — план реализации и проверки

Статус реализации: пользователь разрешил весь набор T-01–T-17 одним проходом. Все функции подтверждённого MVP реализованы в `main`; фактические статусы задач и ограничения приведены ниже. Авторское прослушивание/оценка дизайна не выдаются за автоматические проверки.

### Сохранение исходной версии

- Старая версия сохранена в локальной и опубликованной ветке `legacy-pinkbox`, коммит `422b9458e61d6b80286068e97bf3ccacbaf32ddb`.
- Новая реализация находится в `/workspace/pinkbox`, активная ветка `main`. Архивная ветка не изменяется.
- Сохранены Bun, JavaScript, Tone 15.1.22 и workaround браузерной сборки. Прежние WAV не используются для нового исполнения; настоящие Synth/PolySynth реализуют утверждённую генерацию и событийный REC.

**Ограничения:** автоматизация не доказывает хорошее звучание на слух и не заменяет авторскую приёмку T-04/T-13/T-17. Цифровой STOP не измеряет аппаратную задержку колонок. Фоновое выступление, сохранение после reload, Safari/Firefox и мобильный звук не заявляются. При наличии этих открытых критериев все 17 задач не называются безусловно принятыми.

## 1. Правила исполнения плана

- SPEC определяет продуктовые требования; ARCHITECTURE описывает технические рекомендации. При расхождении сначала уточнить документы, не выбирать новое поведение молча.
- Вопросы Q-01–Q-20 сохраняются в реестре. Продуктовые зависимости T-01 закрыты прямыми ответами и делегированием; Q-16–Q-18 относятся к последующим задачам. Статус решения не означает, что его техническая реализация испытана.
- Пользователь поручил работать без дополнительных вопросов. Рутинные детали выбирать самостоятельно в подтверждённом scope, фиксируя основание. Последнее поручение пользователя разрешает весь набор 17 задач, сохраняя подтверждённый scope; новые пользовательские функции не добавляются.
- Реализовать только выбранную ветку REC и подтверждённый scope. Не писать одновременно событийный и PCM-движки «на будущее».
- Сохранять рабочие части существующего проекта. Менять исходники только в рамках конкретной разрешённой задачи реализации, не переписывать всё заранее.
- После каждой небольшой задачи проверять затронутое поведение; при поломке исправлять её до перехода к зависимой задаче.
- Тестировать реальные риски и сценарии. Прохождение formatter, syntax check или нулевого числа тестов не подтверждает работу аудио.
- Верификация не требует заранее нового framework или большой инфраструктуры. Инструмент браузерной автоматизации выбирать только при необходимости повторяемых проверок.
- Длительность, timing, память и viewport приняты по делегированию в SPEC §2.3; результаты находятся в таблице выше.

## 2. Последовательные задачи

### T-01. Уточнить продуктовые блокеры и границу MVP

**Статус:** завершена. Подтверждены событийный REC по партиям, 4 такта, безопасная замена, PLAY/STOP, генерация по музыкальным правилам и scope BPM/VOL/FILTER. Оставшиеся детали приняты по поручению «делай без вопросов, как считаешь правильным» и отмечены в SPEC §2.2/D-17/D-18. T-02 выполнена по делегированию; следующие задачи имеют фактические статусы в таблице выше.

**Фактически проверено:** согласованность трёх документов; закрытие всех продуктовых вопросов этой задачи либо исключение функции из MVP; покрытие 10 FR, 7 NFR, 5 сценариев и реестра Q; наличие зависимостей/критериев/проверок у 17 основных и 2 отложенных задач. Старые неподтверждённые статусы REC/MVP удалены. Git подтвердил активную main, сохранённый исходный коммит legacy-pinkbox и отсутствие изменений файлов приложения. Это приёмка T-01, не утверждение о готовности нового аудио.

**Зависимости:** нет; вход — SPEC. На этом шаге приложение не пишется.

**Результат:** решения по записи отдельной партии/микса, событиям/аудио, длительности и границам REC, сохранению тембра, повторной записи, влиянию гармонии, транспорту и музыкальному вступлению. Отдельно выбрать роли, минимальные выразительные действия, начальный сценарий, роль DRUMS и включение предварительных controls. Уточнить аудиторию. Nopia исследовать по доступным подтверждённым источникам; если доступа нет, явно согласовать использование описанного сценария Pinkbox без обещания точной копии инструмента.

**Критерии приёмки:** выбран один понятный сценарий REC; показан пример «сохранить основу → добавить и изменить наложение → убрать его → завершить». Утверждён перечень первой версии. Каждый влияющий на ближайшие задачи вопрос имеет явный ответ либо отмеченную зависимость; отсутствие ответа не превращено в default.

**Проверка/тест:** прямые ответы пользователя подтверждают REC, PLAY/STOP, генерацию и scope (D-10–D-16); D-17 разрешает самостоятельно принять оставшиеся детали. Демонстрационный сценарий зафиксирован: PLAY/KEYS → записать 4 такта → добавить BASS/ARP/SYNTH → менять FILTER/BPM → убрать слои → STOP. Проверяется согласованность SPEC/ARCHITECTURE/PLAN и покрытие требований; новое аудиоповедение пока не реализовано и не испытано. Музыкальная приёмка материала остаётся T-04.

**Покрытие:** FR-01, FR-04–FR-08, SPEC §4.1, §7–§10; Q-01–Q-15, Q-19–Q-20. Музыкальные материалы и технические бюджеты окончательно принимаются в T-04/T-02.

### T-02. Согласовать условия и измеримые пороги приёмки

**Зависимости:** можно начать после чтения SPEC; окончательно завершить после T-01.

**Результат:** матрица браузеров/устройств, реальные размеры области браузера, правила фоновой вкладки, требования доступности, допустимая задержка управления и остановки, допуск рассинхрона, длительность выступления, число повторов и бюджет памяти. Список основных сочетаний для проверки конкретизируется после T-04.

**Критерии приёмки:** для NFR-02, NFR-04–NFR-07 заданы условия и пороги; ясно, что поддерживается и что остаётся ограничением. Не обещана работа на непроверенных устройствах. Нужный сценарий завершения задаёт измеримую длительность хвоста/момент тишины.

**Проверка/тест:** по делегированию D-17 выбрать и зафиксировать матрицу/способ измерения без повторного опроса. Проверить непротиворечивость: один экран должен одновременно допускать читаемость, доступные controls и выбранный scope. Принятие бюджетов не означает, что приложение уже соответствует им.

**Покрытие:** FR-03, FR-04; NFR-02, NFR-04–NFR-07; Q-16–Q-18.

### T-03. Проверить техническую реализуемость выбранной записи

**Зависимости:** выбранная ветка из T-01, контрольное окружение T-02. Выполнение разрешено на этапе IMPLEMENTATION.

**Результат будущей задачи:** минимальная техническая проверка одной нотной фразы, её событийной записи на 4 такта, повторения и немедленного STOP с текущей Tone 15.1.22. Проверить устойчивость содержимого, note-off, музыкальные границы и публичную отмену будущих источников выбранного инструмента. PCM-ветка не реализуется.

**Критерии приёмки:** запись проходит несколько циклов, не запускает новую случайную фразу и укладывается в согласованные допуски. STOP не оставляет будущую атаку и сохраняет готовую фразу. Изменение тембра не меняет сохранённые ноты/ритм. При неудаче вернуться к конкретному решению T-01, не скрывать ограничение.

**Проверка/тест:** браузерный probe и прослушивание; сравнение длительности/позиции с аудиовременем; отдельный STOP внутри lookahead. Результаты записаны как наблюдения, не как завершённая функция продукта. Чистую логику можно тестировать Bun; это не замена browser audio.

**Покрытие:** FR-03, FR-04; NFR-05, NFR-07; риски SPEC §11 и ARCHITECTURE §10.

### T-04. Подготовить и принять один музыкальный мир

**Зависимости:** решения о ролях/источнике/гармонии T-01; границы поддерживаемого материала подтверждены T-03.

**Результат:** выбранные тембры и фразы, роли и диапазоны, длины, начальное сочетание и перечень контрольных сочетаний. Не создавать обязательный банк из 16 старых паттернов. Отдельно согласовать действия, дающие развитие и кульминацию.

**Критерии приёмки:** автор принимает начальные материалы и их совместное звучание; роли различимы. Получение хорошего начального результата не требует настройки тональности пользователем. Возможность развития продемонстрирована на материале, не только перечислена в UI.

**Проверка/тест:** совместное прослушивание автора; проверка всех выбранных контрольных сочетаний. Для нотного материала — автоматическая проверка диапазонов, длины и допустимых нот; для WAV — проверка метаданных и музыкального цикла. Автоматическая проверка не выдаётся за доказательство качества композиции.

**Покрытие:** FR-01, FR-02, FR-06, FR-07, S-01, S-04; Q-08–Q-11, Q-14.

### T-05. Ввести единое состояние и проверяемые переходы

**Зависимости:** T-01, T-03; структура материала из T-04.

**Результат:** контроллер состояния готовности, исполнения, REC и партий; намерение/pending отделено от фактического действия. Аудиообъекты отделены от обычных данных. Есть поколение исполнения для устаревших результатов.

**Критерии приёмки:** переходы соответствуют утверждённой семантике; недопустимые команды не запускают звук. STOP/ошибка во время запуска или finalization не позволяет позднему результату восстановить running. Повторные клики не удваивают сессию.

**Проверка/тест:** unit-тесты на последовательности действий, повторные команды, устаревшие поколения и ошибки. Проверить независимость состояния сохранённой фразы от текущего состояния REC. Не добавлять persistence или историю undo, если они не согласованы.

**Покрытие:** FR-04, FR-05; NFR-03, NFR-06.

### T-06. Подготовить аудиосессию и одну звучащую партию

**Зависимости:** T-03–T-05.

**Результат:** один AudioContext/Transport, один выбранный источник, загрузка необходимого материала, запуск после пользовательского действия и реестр ресурсов. Существующий Bun browser bundle продолжает работать.

**Критерии приёмки:** открытие страницы молчит; одно разрешённое действие запускает согласованную фразу. До готовности не показывается running. Повторная подготовка не создаёт новые экземпляры без необходимости. Загрузка/разблокировка контекста имеет различимый результат.

**Проверка/тест:** реальные запросы страницы, стилей, bundle и нужных assets; запуск в выбранном браузере и прослушивание. Browser-тест для отсутствия autoplay и повторного START; проверить реальное число созданных контекстов/источников, а не только DOM-индикатор.

**Покрытие:** FR-01; NFR-05, NFR-06; S-01; технические ориентиры SPEC §6.

### T-07. Реализовать один музыкальный планировщик и границы

**Зависимости:** T-05, T-06; решения о ticks, длинах и границах T-01/T-04.

**Результат:** общий расчёт позиции, события через callback time, цикл 4 тактов и pending-действия на начале такта. Включить применение общего BPM 120/60–160 с сохранением высоты и музыкальной длины REC. Никаких отдельных timers для партий.

**Критерии приёмки:** вступление не назначается задним числом; повторные клики не дают двойных стартов. На границе цикла нет пропуска/двойного исполнения события. Время аудиособытия не зависит от UI-отрисовки. Длительные ноты и note-off соответствуют выбранной политике.

**Проверка/тест:** unit-тесты границ «до/на/после», lookahead и некорректного BPM; две партии на общей сетке в браузере. Изменить BPM до записи, во время REC и повторения, включая 60/120/160; проверить note-off, ровно 4 такта и неизменные ноты. Сравнить аудиовремена с условиями T-02 и повторить под нагрузкой UI. Логов вызовов недостаточно для вывода об отсутствии слышимых сбоев.

**Покрытие:** FR-03, FR-05, FR-09; NFR-05; Q-03, Q-06, Q-13.

### T-08. Обеспечить безопасную остановку и повторный старт

**Зависимости:** T-05–T-07; публичные API отмены проверены T-03; политика транспорта принята T-01.

**Результат:** протокол STOP из ARCHITECTURE §7.3, очистка принадлежащих сессии событий, отмена/изоляция будущих источников, контролируемые release/fade и защита от старых поколений. PAUSE/RESET реализуются только если утверждены, с собственной семантикой.

**Критерии приёмки:** STOP идемпотентен. Нет «призрачных» атак после согласованного момента остановки. Хвосты и позиция соответствуют принятой политике. START после STOP не удваивает расписание, инструменты или старый буфер. Не происходит неожиданного удаления пользовательских записей.

**Проверка/тест:** браузерные случаи немедленного STOP перед будущей атакой, во время длинной ноты, перед концом цикла, во время подготовки и дважды подряд; серии START/STOP. Не должно быть ожидания такта. При выбранных эффектах повторить с хвостом; после T-09 добавить STOP при REC/finalization. Проверить сохранность готовых фраз и старт с начала, звук и реестр ресурсов, не только Transport.state.

**Покрытие:** FR-03, FR-07; NFR-05; S-05; Q-04, Q-12–Q-13.

### T-09. Реализовать выбранный REC и бесшовное повторение

**Зависимости:** T-03–T-08; закрытые для этой задачи Q-01–Q-04.

**Результат:** запись нот/ритма выбранной партии с начала такта за 4 такта, атомарная публикация и автоматическое повторение. На партию один слот; повторный REC заменяет его только при успехе. Ошибка/STOP сохраняют предыдущую фразу. Выполняется событийная реализация ARCHITECTURE §6.

**Критерии приёмки:** повторяется сохранённая фраза; live-источник и его копия не дублируют звук непреднамеренно. Длина точна в согласованном допуске; цикл не имеет разрыва. Пользователь может продолжать работать. Ошибка/отмена/late finalization не считается успешной записью. Повторная запись, удаление и отмена включены только в принятом объёме.

**Проверка/тест:** сравнить сохранённое содержимое с исполненными событиями нескольких циклов и проверить ровно 4 такта. Проверить события на обеих границах и пересекающие её ноты. Browser-сценарии REC → повтор → STOP/START, повторная запись с успехом/ошибкой и завершение старого поколения; проверить сохранность старого слота при прерывании и изменение тембра без изменения нот/ритма.

**Покрытие:** FR-04; NFR-03, NFR-05, NFR-06; S-02.

### T-10. Подключить согласованные роли и управляемые наложения

**Зависимости:** T-04–T-09.

**Результат:** KEYS/SYNTH/BASS/ARP в утверждённом наборе с различимым характером; введение и удаление наложений на повторяющуюся основу. Независимая запись выбранной партии согласована в Q-01.

**Критерии приёмки:** добавление/удаление партии не перезапускает основу. Все выбранные роли сохраняют общую фазу. Удаление поздней партии оставляет основу звучать. Начальные сочетания соответствуют принятому музыкальному миру; число вариантов не наследуется автоматически от старых pads.

**Проверка/тест:** каждое контрольное сочетание T-04; ввод на разных позициях цикла, повторные переключения и максимальный выбранный набор одновременно. Автоматические проверки ожидаемых событий плюс реальное прослушивание. Проверить границы совпадающих/разных длин, только если разные длины разрешены.

**Покрытие:** FR-02, FR-03, FR-05, FR-06; S-03, S-04.

### T-11. Добавить минимальные выразительные преобразования и выход

**Зависимости:** T-01, T-04, T-08–T-10.

**Результат:** общий VOL 0–100% (исходно 80%) и low-pass FILTER каждой роли, управляющий выбранной партией. UI FILTER 0–100% (исходно 100%, открытый). Один эффект на роль; REC сохраняет события без автоматизации параметров. BPM реализуется T-07.

**Критерии приёмки:** FILTER меняет только выбранную партию, не переписывая сохранённые события. Общая громкость влияет на весь микс без его перезапуска; 0% даёт тишину, но Transport/фразы сохраняются. Регуляторы не создают новые инструменты и не вызывают непредусмотренных щелчков. Проверен немедленный STOP после регулировки.

**Проверка/тест:** параметры на границах согласованных диапазонов; быстрые и медленные движения; запись до/после преобразования по выбранной семантике; прослушивание. Измерить максимальную комбинацию по T-02. Не реализовывать полный набор FX ради проверки возможного будущего расширения.

**Покрытие:** FR-05, FR-07, FR-08, FR-10; NFR-05; S-03, S-04.

### T-12. Связать UI с состоянием и доступными действиями

**Зависимости:** T-05–T-11.

**Результат:** UI-команды через контроллер; distinct loading/ready/error, pending/active и recording/saved. Индикация музыкального события следует аудиовремени. Семантические controls, доступные имена, фокус и клавиатура.

**Критерии приёмки:** REC не выглядит активным до начала захвата; ошибка не выглядит успешной записью. Наложения и основа различимы. Рендер музыкальной позиции не сбрасывает фокус или текущую регулировку. Основные действия доступны без мыши; состояние не зависит только от цвета. Нет повторяющихся значений без причины.

**Проверка/тест:** браузерные сценарии с клавиатуры, проверка accessible names и состояния; повторные клики во время pending/loading/REC. Сопоставить момент UI-индикации с аудиовременем; screen reader не получает уведомление на каждую долю.

**Покрытие:** NFR-03, NFR-04, NFR-06; интерфейс сценариев S-01–S-05.

### T-13. Оформить аппаратный интерфейс на одном экране

**Зависимости:** T-02, T-12; выбранные визуальные приоритеты T-01.

**Результат:** pink hardware-inspired оформление и компоновка всех существенных controls на согласованной области браузера. Не добавлять декоративные секции или подписи для заполнения экрана.

**Критерии приёмки:** автор принимает стиль; все существенные элементы видимы без вертикального scroll на основном размере. Читаемость, focus и keyboard сохраняются. На остальных заявленных размерах поведение соответствует выбранным компромиссам; их нельзя скрыть уменьшением до непригодного размера.

**Проверка/тест:** screenshot review на согласованных viewport, фактические размеры scroll area и controls, измерение контраста, проход с клавиатуры. Полный визуальный дизайн не считается утверждённым только по автоматической проверке геометрии.

**Покрытие:** NFR-01–NFR-04.

### T-14. Проверить ошибки, приостановку и повторную инициализацию

**Зависимости:** T-05–T-09, T-12; политика окружения T-02.

**Результат:** согласованная обработка неуспешной загрузки/запуска/REC, AudioContext suspension и возврата из фоновой вкладки. Если retry выбран, он переиспользует корректное состояние без дублирования слушателей.

**Критерии приёмки:** ошибки не дают ложных running/saved. Старые async-операции не запускают новую сессию. Возврат из фона соответствует согласованной политике и не вызывает шквал просроченных событий. Отказ браузера в запуске не маскируется индикатором PLAY.

**Проверка/тест:** принудительный отказ ресурса и запуска контекста, прерывание REC, скрытие/возврат вкладки в каждом заявленном браузере; повторить инициализацию/восстановление по выбранной политике. Условия воспроизведения и ограничения фиксируются.

**Покрытие:** NFR-05–NFR-07; S-01–S-03 в ошибочных условиях.

### T-15. Измерить устойчивость, нагрузку и жизненный цикл

**Зависимости:** T-02, T-08–T-14; C-01/C-02 только если включены и выполнены.

**Результат:** проверка максимального согласованного набора партий/голосов, частых действий и длительного выступления. Декодирование, DOM и тяжёлые операции не выполняются в музыкальном callback.

**Критерии приёмки:** задержки, рассинхрон, STOP, память и отзывчивость укладываются в пороги T-02. Повторная запись/замена/START/STOP не оставляет неограниченно растущий список голосов, schedule IDs, буферов или listeners. Пики громкости не дают непредусмотренных искажений.

**Проверка/тест:** browser profiling и resource counters на согласованном числе циклов; контроль baseline после завершения и освобождения ресурсов. Память процесса сама по себе может не сразу падать из-за GC — проверять живые ссылки и устойчивый trend. Сопоставить запланированные timestamps с offline/browser-сигналом там, где возможно, и прослушать реальное устройство. Результат не объявляется успешным по одним логам планировщика.

**Покрытие:** FR-03, FR-04; NFR-05, NFR-07.

### T-16. Пройти матрицу совместимости и итоговые регрессии

**Зависимости:** T-02, T-13–T-15; все включённые условные задачи.

**Результат:** воспроизводимые проверки выбранных браузеров, устройств, viewport, клавиатуры и звука. Повторно проверить замороженный install по lockfile и реальный Bun browser build, если зависимости/сборка менялись.

**Критерии приёмки:** все включённые требования имеют результат в каждом заявленном окружении. Неисполненные, проваленные и исключённые по scope проверки различаются. Нет заявления о мобильной/фоновой поддержке без проверки.

**Проверка/тест:** основной набор S-01–S-05 и негативные сценарии T-08/T-09/T-14; geometry/keyboard/contrast. Зафиксировать точные версии окружений. Не расширять матрицу на не согласованные платформы ради формального количества проверок.

**Покрытие:** NFR-02, NFR-04, NFR-06, NFR-07; все применимые FR.

### T-17. Принять полноценное выступление и границу первой версии

**Зависимости:** T-04, T-10–T-16; закрытые продуктовые вопросы, влияющие на включённые функции.

**Результат:** демонстрационное выступление автора с сохранённой фразой и управляемыми наложениями: начало → развитие → кульминация → завершение. Финальный отчёт о требованиях и ограничениях.

**Критерии приёмки:** автор достигает этих этапов без ручной игры нот и ритма; музыка развивается в ответ на действия. Начальные сочетания приняты на слух. Запись сохраняет фразу; её наличие не блокирует дальнейшее выступление. Согласованные проверки пройдены, а нерешённые ограничения не скрыты.

**Проверка/тест:** авторское прослушивание и прохождение S-01–S-05; сверка матрицы покрытия ниже с фактическими результатами. Запись/экспорт выступления как пользовательская функция не требуется для этой проверки. При провале вернуться к конкретной задаче, а не заменить сценарий тривиальной демонстрацией PLAY.

**Покрытие:** FR-01–FR-10, NFR-01–NFR-07; итоговая продуктовая цель SPEC §2.

## 3. Условные задачи: не входят автоматически

### C-01. PITCH / KEY / SCALE — отложено

**Условие включения:** отдельное будущее изменение scope. По итогам T-01 PITCH/KEY/SCALE отложены. BPM уже включён в основной T-07 и не зависит от C-01.

**Зависимости:** T-01–T-04, T-07–T-11. При включении завершить до итоговой проверки T-15–T-17.

**Результат:** только выбранные регуляторы, их диапазоны, область действия и поведение сохранённой фразы. Не наследовать 120/60–160 или ±12 как утверждённые значения.

**Критерии приёмки:** изменения следуют музыкальному времени; сохранённая основа меняется либо остаётся фиксированной по принятому решению. SCALE изменяет музыкальную модель, а не только label или общую высоту. Изменение BPM не подменяется изменением скорости целого WAV вместо исполнения сохранённых событий.

**Проверка/тест:** unit-тесты нотных преобразований и будущих note-off; браузерные изменения на границе и в середине цикла, во время REC, на крайних выбранных значениях; совместное прослушивание записанной основы и наложений. После изменения темпа проверять не только старт цикла, но и события внутри него.

**Покрытие:** SPEC §4.1, Q-05–Q-07; FR-02, FR-03, FR-04, FR-05 при наличии этих controls.

### C-02. Визуализатор

**Условие включения:** отдельное будущее изменение scope. Пользователь отложил визуализатор; C-02 не выполняется в MVP. Просьба описать архитектуру не является обязательством реализовать.

**Зависимости:** T-02, T-06, T-11–T-13. При включении завершить до T-15–T-17.

**Результат:** минимальная индикация выбранного сигнала, один analyser и визуальное обновление, не управляющее звуком.

**Критерии приёмки:** показ соответствует точке аудиографа; его отключение не влияет на музыку/REC. Отрисовка приостанавливается в фоне и не превышает бюджет T-02. Нет нового обязательного элемента вне viewport.

**Проверка/тест:** сравнение тишины/звучания, нагрузка с включённой и выключенной отрисовкой, скрытие вкладки и очистка analyser/rAF. Не добавлять несколько видов спектра или waveform без требования.

**Покрытие:** условная возможность SPEC §8, NFR-02, NFR-05.

Сохранение проектов, экспорт, дополнительные миры, MIDI-вход и публикация записей не имеют задач реализации в этом плане. Эффекты входят только в выбранный минимальный набор T-11, а PAUSE/RESET — только в выбранную семантику T-08. Для DRUMS потребуется отдельное согласование scope; текущий план не создаёт их автоматически.

## 8. Проверка границы плана

Все FR-01–FR-10, NFR-01–NFR-07 и S-01–S-05 имеют задачи и способ проверки. Q-01–Q-15, Q-19/Q-20 закрыты для MVP ответами и делегированием; Q-16–Q-18 конкретизированы в SPEC §2.3; авторская приёмка T-13 остаётся открытой. Scope изменён только по прямому подтверждению, детали — по D-17, а не автоматически.

Включены только подтверждённые пользователем функции; BPM и FILTER получили критерии FR-09/FR-10. Поколение исполнения, реестр ресурсов, pending commands и технические проверки — средства обеспечения этих требований, а не расширение продукта. Визуализатор и остальные FX остаются отложенными.

План покрывает требование только как предстоящую работу. Готовность первой версии объявляется после выполнения применимых задач и приёмки, а не после создания этих документов.
